## 1. The Sequential State Machine

### Location

`app/src/analyzers/universal/UniversalSchemaAnalyzer.ts:280-301`

### Implementation

```typescript
private processMigrationSource(
  source: string,
  tables: Set<string>,
): void {
  const ddlRe = /(CREATE)\s+(?:VIRTUAL\s+)?TABLE\s+(?:IF\s+NOT\s+EXISTS\s+)?(`[^`]+`|"[^"]+"|\w+)|(DROP)\s+TABLE\s+(?:IF\s+EXISTS\s+)?(`[^`]+`|"[^"]+"|\w+)|(ALTER)\s+TABLE\s+(`[^`]+`|"[^"]+"|\w+)\s+RENAME\s+TO\s+(`[^`]+`|"[^"]+"|\w+)/gi;

  let match: RegExpExecArray | null;
  while ((match = ddlRe.exec(source)) !== null) {
    const op = match[1] || match[3] || match[5];
    if (op === 'CREATE') {
      tables.add(this.stripIdentifier(match[2]));
    } else if (op === 'DROP') {
      tables.delete(this.stripIdentifier(match[4]));
    } else if (op === 'ALTER') {
      tables.delete(this.stripIdentifier(match[6]));
      tables.add(this.stripIdentifier(match[7]));
    }
  }
}
```

### DDL Regex Capture Groups

| Group | Operator | Table Name | Meaning |
|-------|----------|------------|---------|
| 1, 2 | CREATE | `match[2]` | Add table to catalog |
| 3, 4 | DROP | `match[4]` | Remove table from catalog |
| 5, 6, 7 | ALTER RENAME | `match[6]` → `match[7]` | Remove old name, add new name |

The regex handles:
- **`CREATE VIRTUAL TABLE`**: `(?:VIRTUAL\s+)?` — FTS tables (recall-protocol's `strategies_fts`) enter the catalog
- **`CREATE TABLE IF NOT EXISTS`**: `(?:IF\s+NOT\s+EXISTS\s+)?` — conditional creation
- **Quoted identifiers**: `` `table_name` ``, `"table_name"`, and unquoted `table_name`
- **`DROP TABLE IF EXISTS`**: Same optional `(?:IF\s+EXISTS\s+)?` group

### Processing Order

`discoverTablesFromMigrations()` walks SQL files matching `fileGateGlobs` (from wrangler config), sorted alphabetically. For each file, `processMigrationSource()` applies the state machine **statement by statement** — not three-pass (all CREATE first, then all DROP, then all RENAME).

## 2. The Old Approach and Its Bug

### Old Three-Pass Approach (Removed)

```
Pass 1: Find all CREATE → add to catalog
Pass 2: Find all DROP  → remove from catalog
Pass 3: Find all RENAME → remove old, add new
```

### The Rename-Replay Bug

In the old approach, if a migration **renamed a table then recreated it fresh** in the same file:

```sql
ALTER TABLE posts RENAME TO posts_hist;
CREATE TABLE posts (id INTEGER PRIMARY KEY, ...);
```

- Pass 1: `posts` added (CREATE seen), `posts_hist` NOT added (no CREATE for it)
- Pass 3: `posts` removed, `posts_hist` added
- **Result**: `posts` from the CREATE was silently deleted by the RENAME. Catalog has `posts_hist` only.

With the sequential state machine:
- Statement 1 (ALTER): `posts` removed, `posts_hist` added
- Statement 2 (CREATE): `posts` added
- **Result**: Both `posts` AND `posts_hist` in catalog. ✅

This pattern occurs in recall-protocol migration 0129 for tables `stadium_build`, `stadium_cap`, `stadium_lookup`, `stadium_exp`, and `stadium_data`. Five tables are renamed to `_hist` variants, then recreated fresh by the same migration file.

# Spec Item 3 — sql-injection-risk Receipt Shapes Evidence

**Date**: 2026-07-28 (session continued from 2026-07-25)
**Version**: v3.4.8
**Findings**: 78 `sql-injection-risk` violations across 23 files

## Verdict

All 78 findings are **false positives** — zero actual SQL injection vulnerabilities.
Three distinct receipt shapes identified. No code fixes; receipted closure with
known architectural constraint.

## Root Cause

The detection pipeline in `checkQuerySecurity()` (UniversalDataAccessAnalyzer.ts:720-798):

1. `getDynamicParts()` extracts template-literal expressions from SQL strings
2. For each dynamic part with `isIdentifier`, calls `resolveLocalConstant()` to determine if it resolves to a compile-time constant
3. `resolveLocalConstant()` is intentionally **local-only** — it resolves `const FOO = "literal"` in the same file but cannot trace imports from other files or through function calls

The constraint is architectural, not accidental: cross-module constant resolution requires
full-program type analysis (TS server), which is out of scope.

## Receipt 1 — Imported SQL Fragment Constants (~30 findings)

**Message pattern**: `Potential SQL injection risk in [prepare|COUNT]. Use parameterized queries.`
**Root cause**: Template literals with `${IMPORTED_CONSTANT}` where the constant is defined in another module.

**Exemplar**: `src/lib/admin-asset-rehost.ts:117`
```typescript
// In src/lib/hero-source-filter.ts (separate module):
export const OFFICIAL_HEROES_SQL = "user_id IS NULL";

// In src/lib/admin-asset-rehost.ts:
import { OFFICIAL_HEROES_SQL } from './hero-source-filter';
// ...
const sql = `SELECT ... WHERE ... AND ${OFFICIAL_HEROES_SQL}`;
//                                  ^^^^^^^^^^^^^^^^^^^
//                                  flagged: resolveLocalConstant() can't trace import
```

`OFFICIAL_HEROES_SQL` is a compile-time constant string `"user_id IS NULL"` — a static
SQL fragment, explicitly documented as such in the source: "Interpolate the constant into
a WHERE…AND clause rather than binding — it's a static SQL fragment, not user input."

**Affected files**: roster-catalog.ts, hero-data-agent.ts (via import from hero-source-filter.ts)

**Verdict**: FALSE POSITIVE — imported compile-time string constants are safe SQL fragments.

## Finding #1 — `offsetToLocation()` double-counts `base.line` **[FIXED]**

**File**: `src/analyzers/universal/UniversalSchemaAnalyzer.ts:1236-1243`  
**Severity**: Real — produced impossible line numbers (line 67 in a 43-line file).  
**Root cause**: `lineOffset` is 0-based (computed from `split('\n').length - 1`), and was added to `base.line` (a 1-based call-site line). When `base.line = 30` and `lineOffset = 33`, result was 63.  
**Fix**: Replaced `base.line + lineOffset` with `lineOffset + 1`. `lineOffset` is the 0-based absolute line in source text; `+1` yields the correct 1-based line independent of the base.

```diff
- return { line: base.line + lineOffset, column };
+ return { line: lineOffset + 1, column };
```

**Callers audited**:
1. Line ~855: `offsetToLocation(sourceCode, offset, baseLocation)` — where `baseLocation` is the call expression's 1-based location. Was double-counting. Now correct.
2. Line ~1090: `offsetToLocation(sourceCode, offset, { line: 1, column: 1 })` — was accidentally correct before (1 + N ≈ N + 1 in many cases), now explicitly correct.

**Verification**: Tarball audit against `bench/recall-fixture/queries.ts` (43 lines):
- `unknown-table` on `"quoted_table"` now reports line 34 ✓ (was line 67)
- All 29 violations report lines in range [1, 43] ✓

## Finding #2 — `collectErrors()` stores 0-based positions **[FIXED]**

**File**: `src/languages/adapterBridge.ts:72-82`  
**Severity**: Minor — parse error positions were 0-based. In practice, no consumer reads `.line`/`.column` from these errors; only `.message` is consumed. But the comment at `astParser.ts:84` incorrectly claimed they were 1-based ("toSourceLocation() now returns 1-based positions").

+ end: { line: node.endPosition.row + 1, column: node.endPosition.column + 1 },

---

## 4. The JSX Gate — Primary Root Cause of Zero

The tree-sitter-based `isFunctionalComponent()` in `componentScanner.ts` requires `returnsJSX()` — the function body must contain `jsx_element`, `jsx_fragment`, or `jsx_self_closing_element` AST nodes.

**Consequence**: A `.ts` or `.js` file without inline JSX is invisible to the React analyzer. The old TypeScript Compiler API approach could do cross-file type resolution (return type of `React.FC<Props>` → component); tree-sitter walks a single file's AST and has no type information. If your project uses `.ts`/`.js` without JSX, or returns JSX through helper functions:

→ **Zero components detected → zero violations emitted.**

| Rule | Gate | Likelihood of firing |
|------|------|---------------------|
| `hooks-naming` | Custom hooks starting with something other than `use` | Low — most projects follow this convention |
| `hooks-violation` | Hook call outside component body | Near-zero — conditional hook check was removed (Spec-17 R6) due to 100% FP rate |
| `no-error-boundary` | >10 components AND 0 error boundaries | Rare — needs specific project shape |
| `accessibility` | Interactive element without ARIA attributes | Depends on JSX scanning; needs `checkAccessibility: true` |
| `raw-element` | `<div>` without semantic role | Gated on `wrapperMinUsages` threshold |

---

## 6. Sweep Parameter Mismatch

The sweep in `runBench.ts:1557` defines `maxComponentComplexity` with `shippedDefault: 15`, but `DEFAULT_REACT_CONFIG` uses `maxComponentComplexity: 10`. Sweep-mode recommendations for complexity thresholds are off by 5 relative to actual user-facing defaults.

---

## 7. Verdict

The React analyzer is **not broken** — it correctly detects complexity violations in the bench corpus and would detect them in real projects with inline JSX. But it will produce **zero or near-zero findings** on many real projects because:

1. **JSX gate**: No JSX in file → component not detected (tree-sitter limitation, no cross-file types)
2. **2 of 7 rules default-off**: `missing-props` and `performance` never fire without explicit config
3. **Threshold gates**: `no-error-boundary` needs >10 components + 0 boundaries; `hooks-naming` only fires on non-standard naming
4. **Hooks gutted**: Conditional hook check removed (Spec-17 R6) — only naming and body-position checks remain
5. **Bench tests 1 rule**: F1=1.0 says nothing about real-world behavior for the other 6

### Recommendations

1. **Consolidate rules**: Drop rules the analyzer can't reliably detect (hooks-related after Spec-17 R6 gutting) or document as low-signal
2. **Increase bench coverage**: Add fixtures for `accessibility`, `hooks-naming`, `no-error-boundary`, `raw-element`
3. **Fix sweep default**: Align `maxComponentComplexity` shipped default with analyzer default (both 10, not 15)
4. **Honest documentation**: Document the JSX gate limitation — `.ts`/`.js` files without JSX will produce zero React findings

## 2. Tailwind v4 Package Resolution Bug

### Finding

The compile-probe fails to initialize against a real Shadcn-style fixture with Tailwind v4.3.3 installed. Both v4 and v3 paths fail.

**Test fixture**: `app/bench/corpus/shadcn-jit/` — `package.json` with `"tailwindcss": "^4.0.0"`, Shadcn-style `app.css` with `@theme` block, and a component file with 32 test classes spanning Shadcn semantic theme, standard utilities, opacity modifiers, variant combinations, and JIT arbitrary values.

**Result**:
```

  (neither v4 compile() nor v3 resolveConfig detected)" }
```

### Diagnosis

**v4 path fails**: `tryImportV4()` at `tailwindProbe.ts:448-466`:

```typescript
// Attempt 1: imports the directory as a file:// URL
return await import(pathToFileURL(twPath).href);
// → Error: Cannot find module '...tailwindcss/index.js'
```

Tailwind v4.3.3 has no `index.js` — it uses `package.json` `exports`:
```json
{ "exports": {
    ".": {
      "import": "./dist/lib.mjs",
      "require": "./dist/lib.js"
    }
  }
}
```

`import()` on a directory only works if `package.json` has a `main` or `module` field (or `index.js`). v4 has neither.

```typescript
// Attempt 2: bare specifier import
return await import('tailwindcss');
// → Resolves from the analyzer's execution path (app/), NOT the project root
```

`import('tailwindcss')` resolves from the process CWD or the module resolution path of the running script. When `code-auditor-mcp` is installed globally via npm and invoked against a user's project, the bare specifier resolves from the global install location — where `tailwindcss` is not a dependency. The comment in the code says "resolved at runtime from the audited project" — this is **wrong**; Node.js ESM `import()` does not search the audited project's `node_modules` unless the CWD IS the project.

**v3 path fails**: The v3 fallback at line 155:
```typescript
const projectRequire = createRequire(join(projectRoot, 'package.json'));
const tw = projectRequire(twPath);
```

Tailwind v4.3.3's `dist/lib.js` (the CJS entry) exports `{ compile, compileAst, Features, ... }` — NOT a function. The v3 check:
```typescript
if (typeof tw === 'function' || (tw.default && typeof tw.default === 'function')) {
```
fails because `tw` is `{ compile: [Function], ... }`, not a function. The `default` export exists but is also not callable in the CJS build.

### Impact

The compile-probe fails on **every** project using Tailwind v4. The fail-open design is respected: `expander.configFailed` → `true` → `detectUndefinedClasses` emits `styles/undefined-class-disabled` (a warning) and returns early. **No false positives are emitted** — but the undefined-class detector is **permanently disabled** for all v4 users.

## 3. What v4 `compile()` CAN Validate (When Probe Works)

Testing with a direct import from the fixture's CWD confirms that `tailwindcss/compile` works and validates classes correctly:

```
import('tailwindcss') succeeded:
  compile: function
  compileAst: function
```

When `compile()` works (e.g., `compile(Buffer.from('@import "tailwindcss";\n.p0{@apply flex;}'))`):
- **Standard utilities** (`flex`, `rounded-lg`, `px-4`, `py-2`): validate correctly — they produce CSS declarations
- **Shadcn semantic theme classes** (`bg-background`, `text-foreground`): validate correctly — `resolveConfig()` exposes custom theme colors defined via `@theme` or `tailwind.config.*`
- **JIT arbitrary values** (`w-[73px]`, `bg-[#123456]`): handled structurally by `matchesArbitraryValue()` in `TailwindUtilityExpander.resolve()` — NOT by the probe. ARBITRARY_VALUE_RE = `/^[a-z][\w-]*-\[.+\]$/i`.

### Classes and Their Resolution Tiers

| Class Family | Resolution Tier | Probe Required? |
|-------------|----------------|-----------------|
| Standard utilities (`flex`, `rounded-lg`) | probe cache (v4 `compile()` or v3 `resolveConfig()`) | Yes |
| Shadcn semantic theme (`bg-background`) | probe cache (v4 `compile()` or v3 `resolveConfig()`) | Yes |
| Arbitrary values (`w-[73px]`) | structural (`arbitrary-value` tier) | No |
| Opacity modifiers (`bg-red-500/50`) | structural + probe prefix check | Partial (prefix must validate) |
| Variant combos (`hover:bg-accent`) | structural (strip variant, re-resolve) | Partial (base must validate) |
| Negative utilities (`-mt-2`) | structural (`negative-utility` tier) | Partial (positive must validate) |

## 4. Fix Required

### Fix A — v4 Package Resolution (P0 — release-blocker)

`tryImportV4()` must resolve the entry point from `package.json` exports rather than importing the directory:

```typescript
private async tryImportV4(twPath: string): Promise<Record<string, unknown> | null> {
  // Read package.json to find entry point
  const pkgPath = join(twPath, 'package.json');
  if (!existsSync(pkgPath)) return null;

  try {
    // v4+ uses package.json exports — resolve the ESM entry point
    const pkg = JSON.parse(readFileSync(pkgPath, 'utf-8'));
    const entry = pkg.exports?.['.']?.import 
      || pkg.module 
      || pkg.main 
      || 'index.js';
    const resolvedPath = join(twPath, entry);
    if (existsSync(resolvedPath)) {
      return await import(pathToFileURL(resolvedPath).href);
    }
  } catch {
    // Falls through to next attempt
  }

  try {
    // Use createRequire to resolve from the project root, then import the resolved path
    const projectRequire = createRequire(join(this.projectRoot, 'package.json'));
    const resolved = projectRequire.resolve('tailwindcss');
    return await import(pathToFileURL(resolved).href);
  } catch {
    return null;
  }
}
```

### Fix B — v3 Fallback for v4 Packages (P1)

The v3 fallback check `typeof tw === 'function'` breaks for v4.3+ where the CJS entry point is an object with named exports. Add a v4-in-CJS check:

```typescript
// Check for v4 CJS exports (mod is { compile, compileAst, ... })
if (tw && typeof tw.compile === 'function') {
  // Confirm compile works with a test
  const result = tw.compile(
    Buffer.from('@import "tailwindcss";\n.p0{@apply flex;}'),
    { base: projectRoot }
  );
  // ... same validation as v4 path
}
```

## 6. JIT: MOOT

**The JIT concern is moot.** JIT arbitrary values (`w-[73px]`, `bg-[#123456]`, `grid-cols-[repeat(3,minmax(0,1fr))]`) are handled structurally by `matchesArbitraryValue()` in `TailwindUtilityExpander.resolve()` — the `ARBITRARY_VALUE_RE` regex matches any `prefix-[...]` pattern. The compile-probe is not needed for JIT class resolution. The probe failure described below (v4 package resolution) affects standard utilities and Shadcn semantic theme classes, not JIT-synthesized values. Users with JIT-heavy Shadcn UI projects get correct `undefined-class` detection for JIT classes even when the probe is disabled.

### Underlying Probe Bug (Not JIT)

The compile-probe has a P0 package-resolution bug with Tailwind v4 (affects standard utilities and `@theme` semantic classes). The fail-open design correctly disables the detector when the probe fails. This bug is **not fixed** — it's a diagnostic finding documented for a future fix.
