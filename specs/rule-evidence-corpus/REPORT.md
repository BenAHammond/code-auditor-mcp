**Root cause of Fix 1.** `hasOrganizationFilter` ran on its own hardcoded

the `data-access-calls` producer with the *default* config (no project config

migrated `missing-org-filter` rule still read the stale default. The fix:

1. `hasOrganizationFilter` moved to `orgFilterTiers.ts` (the pure tenant-scoping

2. The migrated `missing-org-filter` rule recomputes the predicate from
   `queryText` + its resolved thresholds, so predicate detection and tier-set
   discovery read one vocabulary and can never drift.
3. The join exclusion is scoped to join verbs (`innerJoin(x, eq(a.org_id,

`sql` tagged template whose `${…}` carries a string-concatenation interpolation
fires at `critical`, while a `sql` tag whose `${…}` are all bare identifiers
stays quiet — for the *right* reason (parameterized-by-construction), not the
incidental one (the tag's template being a direct child with no `arguments`
node, which the old recursion never reached).

| file:line | before | after | what changed |
|---|---|---|---|
| `sql-injection-surface.ts:126` | — (new) | critical ✓ | new must-fire fixture: ``sql`… LIKE ${'%' + userInput + '%'}` `` — the tag recurses into the interpolation, which is raw string assembly (not a bare id) |

**Root cause of Fix 2.** `isDynamicStringConstruction` treated a tagged template

## Fixed this pass (Fix 5)

Two `loop-query` false negatives — `db.prepare(…).get(…)` inside a loop was not
detected. They had two *distinct* root causes, both now fixed:

| file:line | before | after | root cause |
|---|---|---|---|
| `n-plus-one.ts:51` | quiet (FN) | severe ✓ | the `forEach` callback was never matched as an implicit loop — `isIteratorCallback` extracted the method name with `getNodeText(prop, '')` (empty source) and a `.text`/`.name` payload that web-tree-sitter nodes don't carry, so every iterator callback resolved to `''` |
| `n-plus-one.ts:62` | quiet (FN) | severe ✓ | `.get()` was not in the eager-method set, so `.prepare().get()` was read as statement-construction-only and skipped |

**Fix 5a — `.get()` into the eager set.** `EAGER_DB_METHODS` was the eager
surface `{run, all, first, raw, exec, batch, query}`; `.get()` — the single-row
read shared by better-sqlite3, `node:sqlite`, and `bun:sqlite` — was absent, so
`db.prepare(…).get(…)` was misclassified as statement construction.

**Fix 5b — iterator-callback name extraction.** `isIteratorCallback` relied on
`(node as any).text`/`.name` and `getNodeText(prop, '')` with an empty source,
both of which return nothing for web-tree-sitter nodes, so `.forEach`/`.map`/
`.filter` callbacks were never recognized as implicit loops. It now reads the
property text via `getNodeText(prop, sourceCode)` — the same extraction
`memberPropertyName` uses. This was a dead path that the corpus's `forEach` pin
(`n-plus-one.ts:51`) exposed; the unit test
`spec-17.test.ts` "per-item `.prepare().get()` in a loop fires" and the corpus
now pin both halves.

### Driver-method gap (the report)

The eager set now covers D1's surface plus `.get()`. The eager methods that
better-sqlite3, `node:sqlite`, and `bun:sqlite` expose and D1 does not, and
their coverage status, are:

| driver | eager method | what it does | covered? |
|---|---|---|---|
| better-sqlite3 | `.get()` | single row (or `undefined`) | ✓ Fix 5 |
| better-sqlite3 | `.iterate()` | lazy row iterator | ✗ |
| node:sqlite | `.get()` | single row (or `undefined`) | ✓ Fix 5 |
| node:sqlite | `.iterate()` | lazy row iterator | ✗ |
| bun:sqlite | `.get()` | single row (or `undefined`) | ✓ Fix 5 |
| bun:sqlite | `.values()` | all rows as arrays | ✗ |
| bun:sqlite | `.iterate()` | lazy row iterator | ✗ |

(`.all()` / `.run()` / `.exec()` are already in the set; `.raw()` is both a D1
method and a better-sqlite3 chain modifier, and is covered.)

`.iterate()` (all three) and bun's `.values()` are real eager reads a loop could
abuse, but they are deliberately left out for now: `.iterate()` defers I/O to
the first `.next()`, so a loop that *builds* iterators without consuming them is
not an N+1, and adding it pre-emptively would over-fire until a corpus fixture
proves a false negative. Recorded here as a known gap, not silently dropped.

## Slice 3 — solid/open-closed + dependency-inversion (7/7, no disagreements)

One new module under `corpus/solid/`. `solid/open-closed` reduces over the
`instanceof-targets` fact (Spec 69 R2): one finding per class, anchored at the
class declaration line, when the class body tests `instanceof` against at least
one *domain* type. Two exclusions keep that signal honest, and this corpus pins
both — a built-in exclusion at the producer and an Error-subclass exclusion at
the rule.

### solid/open-closed (7/7) — `solid/open-closed.ts`

| line | kind | expected | actual |
|---|---|---|---|
| 68 | fires | `instanceof` a plain domain type (`PaymentMethod`) | high ✓ |
| 78 | quiet | `instanceof` an Error subclass (`PaymentError extends Error`) — a catch-dispatch guard | quiet ✓ |
| 88 | quiet | `instanceof` an Error subclass whose name does NOT end in "Error" (`PaymentFailure extends Error`) — the extends-chain walk, not a name test | quiet ✓ |
| 98 | fires | `instanceof` a type that merely ENDS in "Error" but does not extend Error (`RecordError`) — name is not sufficient | high ✓ |
| 108 | quiet | `instanceof` a web-platform global (`Response`) — excluded as builtin | quiet ✓ |
| 115 | quiet | `instanceof` a builtin primitive wrapper (`Date`) — excluded | quiet ✓ |
| 122 | quiet | no `instanceof` at all | quiet ✓ |

The two exclusions are pinned independently, not conflated:

1. **Built-ins are excluded at the producer.** `extractInstanceofTargets`
   (`fileSymbols.ts`) drops any target in `BUILTIN_TYPES` — `Date`, `Array`,
   `Map`, the web-platform globals (`Request`/`Response`/`Headers`/
   `ReadableStream`/…), typed arrays, `URL`/`Blob`/`FormData`, and the Error
   family. A class that only tests built-ins never even produces an
   `instanceof-targets` fact, so it never reaches the rule. `HttpGateway`
   (`instanceof Response`) and `Scheduler` (`instanceof Date`) pin this.

2. **Error subclasses are excluded at the rule.** `openClosed`
   (`solid.ts`) runs `isErrorSubclass`, which resolves the target name up its
   `extends` chain against the corpus-wide class declarations (`BUILTIN_ERRORS`
   = Error, TypeError, RangeError, SyntaxError, ReferenceError, EvalError,
   URIError, AggregateError). `PaymentGuard` (`instanceof PaymentError`) and
   `FailureGuard` (`instanceof PaymentFailure`) pin this. Crucially it is *not*
   a `/Error$/` name test: `PaymentFailure` (non-"Error" name, still extends
   Error) quiets, while `RecordError` (ends in "Error", does *not* extend Error)
   fires — the name alone is neither necessary nor sufficient.

### dependency-inversion — tombstoned (documented, not faked)

`dependency-inversion` (old rule 16) is **removed** in Spec 68 —
`ruleAliases.ts` maps `solid/dependency-inversion` → `null`, with the reason that
the concrete-instantiation signal (`new PascalCaseType()` on a non-builtin type)
"does not isolate genuine Dependency Inversion violations; it fires on value
objects/DTOs and factory-builder patterns."

Its real signal — *"a concrete type is instantiated where its interface/abstract
base was declared in-repo"* — requires an "abstraction exists" measurement: does
this `new Concrete()` sit where the code declares an `interface`/`abstract class`
that `Concrete` implements/extends? No current rule computes that predicate, so
the DIP signal is a **documented gap**, not something this corpus fakes. This is
exactly the distinction Spec 68 drew: a measurement that does not isolate a real
defect is removed and *recorded as absent*, rather than kept firing on a proxy.

static fixture. This is the same "cross-run fact can't be pinned statically"

the five raw sites, one per component.

**`maxComponentComplexity` is lowered 20 → 8 in the corpus config** (with a
Spec 36 R5 rationale). The default 20 — calibrated so ordinary multi-branch
components stay quiet — would have kept `CheckoutForm`'s nine branches quiet;
lowering it to 8 lets a realistic component fire without an artificial
twelve-branch monster. The rationale records *why*, so the audit's config gate
accepts the change rather than rejecting it as an unrationalized threshold drift.

**Three react rules are documented gaps, not faked:**

- **missing-props (61)** — gated off by default (`requirePropTypes: false`, since
  TypeScript provides type safety). It can only fire under an explicit
  `requirePropTypes: true` config, which the corpus does not set.
- **no-error-boundary (62)** — app-level: it anchors to a synthetic `app-level`
  file and fires only when the whole corpus has *no* error boundary and more than
  10 components. This corpus totals 10 components (four in `component-smells`,
  six in `raw-elements`), one under the threshold, so the rule stays quiet by
  construction. Its `> 10` boundary and the boundary-present suppression are
  covered by `reactErrorBoundary.spec.ts`, not a per-file header.
- **complexity's circular-dependency arm** — the cross-component half of the
  `complexity` rule anchors to a synthetic `component-dependencies` file (not a
  real source line). No component in the corpus imports another, so the
  component tree is edgeless and no cycle exists to report. The cycle detector
  is covered by unit tests.
