## Fixed this pass (Fix 1)

The five `missing-org-filter` false positives that motivated Fix 1 now match:

| file:line | before | after | what changed |
|---|---|---|---|
| `tenant-scoping.ts:82` | critical (FP) | quiet ✓ | dotted *value* `eq(orders.organizationId, session.orgId)` is a filter, not a join — the blanket "reject any dotted 2nd arg" lookahead is now scoped to join verbs only |
| `tenant-scoping.ts:148` | critical (FP) | quiet ✓ | `workspace_id` is now in the predicate vocabulary (discovery ∪ predicate, one vocabulary) |
| `tenant-scoping.ts:156` | critical (FP) | quiet ✓ | `team_id` recognized via configured `orgFilterColumns` |
| `tenant-scoping.ts:164` | critical (FP) | quiet ✓ | `project_id` recognized via configured `orgFilterColumns` |
| `tenant-scoping.ts:172` | critical (FP) | quiet ✓ | `environment_id` recognized via configured `orgFilterColumns` |

**Root cause of Fix 1.** `hasOrganizationFilter` ran on its own hardcoded
8-name vocabulary while table discovery read the configured `orgFilterColumns`
— two vocabularies for one concept. The predicate detector was also baked into
the `data-access-calls` producer with the *default* config (no project config
reaches a `process(file)` call), so even after unifying the vocabulary, the
migrated `missing-org-filter` rule still read the stale default. The fix:

1. `hasOrganizationFilter` moved to `orgFilterTiers.ts` (the pure tenant-scoping
   module §15 keeps) and driven by `orgPredicateVocabulary` — the same
   lowercased + camelCase-expanded vocabulary `buildOrgFilterTierSet` uses.
2. The migrated `missing-org-filter` rule recomputes the predicate from
   `queryText` + its resolved thresholds, so predicate detection and tier-set
   discovery read one vocabulary and can never drift.
3. The join exclusion is scoped to join verbs (`innerJoin(x, eq(a.org_id,
   b.org_id))`), not blanket "reject any dotted 2nd arg", so a dotted *value*
   (`eq(orgCol, session.orgId)`) is correctly a filter. The Spec 68 JOIN-on-org
   regression still passes.

## Fixed this pass (Fix 2)

The one `sql-injection-risk` false negative that motivated Fix 2 now matches: a
`sql` tagged template whose `${…}` carries a string-concatenation interpolation
fires at `critical`, while a `sql` tag whose `${…}` are all bare identifiers
stays quiet — for the *right* reason (parameterized-by-construction), not the
incidental one (the tag's template being a direct child with no `arguments`
node, which the old recursion never reached).

| file:line | before | after | what changed |
|---|---|---|---|
| `sql-injection-surface.ts:126` | — (new) | critical ✓ | new must-fire fixture: ``sql`… LIKE ${'%' + userInput + '%'}` `` — the tag recurses into the interpolation, which is raw string assembly (not a bare id) |
| `sql-injection-surface.ts:116` | quiet (stale `113` header) | quiet ✓ | the quiet directive now anchors the real DB-call line; `isParameterizedTaggedTemplate` recognizes the bare-id tag as parameterized-by-construction |

**Root cause of Fix 2.** `isDynamicStringConstruction` treated a tagged template
as a `call_expression` and recursed only into its `arguments` node — but for
`sql\`…\`` tree-sitter emits the template as a *direct child* of the call, with no
`arguments` node, so the interpolation inside the tag was never seen. The fix
reaches the direct `template_string` child and recurses; and
`checkQuerySecurity` gains `isParameterizedTaggedTemplate`, which recognizes a
`sql`/`db` tag whose `${…}` interpolations are all bare identifiers as
parameterized-by-construction, so the clean tag stays quiet deliberately rather
than by accident.

## Fixed this pass (Fix 3)

The one `missing-org-filter` false negative that motivated Fix 3 now matches: a
quoted camelCase DDL identifier (`"organizationId"`) survives discovery as a
tenant-scoping column, so the `projects_v2` table is declared and its unscoped
query fires.

| file:line | before | after | what changed |
|---|---|---|---|
| `tenant-scoping.ts:180` | quiet (FN) | critical ✓ | `"organizationId"` → `organizationid` is now recognized by the Tier-3 discovery vocabulary (snake_case + camelCase forms) |

**Root cause of Fix 3.** `buildOrgFilterTierSet` built its `tenantColumns`
vocabulary from `orgFilterColumns` / the default snake_case list *only*, while
the predicate vocabulary (`orgPredicateVocabulary`) expands each name to its
camelCase spelling too. A quoted camelCase DDL column lowercases to
`organizationid` — one token, not `organization_id` — so the tier-discovery half
never saw it and the table was never declared. This is the same "two
vocabularies for one concept" asymmetry §69 Fix 1 closed on the predicate side;
expanding the tier-set vocabulary here closes the discovery half.

## Fixed this pass (Fix 4)

The one `unfiltered-query` false negative that motivated Fix 4 now matches: the
*read* half of `unfiltered-query` was config-declared only (Tier 1 `orgFilterTables`
+ Tier 2 configured schemas) and never consumed Tier 3 DDL-discovered tenant
tables, while the *write* half and `missing-org-filter` both did. A filterless
read of a DDL-only tenant table was therefore missed.

| file:line | before | after | what changed |
|---|---|---|---|
| `raw-sql-access.ts:50` | quiet (FN) | high ✓ | `unfiltered-query` now reads the `table-catalog` fact and its read predicate is driven by the shared `buildOrgFilterTierSet` (all three tiers) |

**Root cause of Fix 4.** `isUnfilteredRead` / `requiresOrgFilter` passed
`undefined` for `ddlTableColumns`, so `buildOrgFilterTierSet` never saw Tier 3.
The fix adds `table-catalog` to `unfiltered-query`'s declared facts and a shared
`buildTierSet` helper in `dataAccess.ts` that `missing-org-filter` and
`unfiltered-query` both call — one tier-set function, three tiers, for the whole
data-access family.

**Side effect.** Reading Tier 3 makes `unfiltered-query` fire on three more
DDL-only tenant-table reads in `tenant-scoping.ts` (the RLS read, the camelCase
read, and the wrapper read). The first two are genuine (`@fires`, lines 123 and
180); the wrapper read (line 117) is the R3 false positive in the working list.

## Fixed this pass (Fix 5)

Two `loop-query` false negatives — `db.prepare(…).get(…)` inside a loop was not
detected. They had two *distinct* root causes, both now fixed:

| file:line | before | after | root cause |
|---|---|---|---|
| `n-plus-one.ts:51` | quiet (FN) | severe ✓ | the `forEach` callback was never matched as an implicit loop — `isIteratorCallback` extracted the method name with `getNodeText(prop, '')` (empty source) and a `.text`/`.name` payload that web-tree-sitter nodes don't carry, so every iterator callback resolved to `''` |
| `n-plus-one.ts:62` | quiet (FN) | severe ✓ | `.get()` was not in the eager-method set, so `.prepare().get()` was read as statement-construction-only and skipped |

**Fix 5a — `.get()` into the eager set.** `EAGER_DB_METHODS` was the eager
surface `{run, all, first, raw, exec, batch, query}`; `.get()` — the single-row
read shared by better-sqlite3, `node:sqlite`, and `bun:sqlite` — was absent, so
`db.prepare(…).get(…)` was misclassified as statement construction.

**Fix 5b — iterator-callback name extraction.** `isIteratorCallback` relied on
`(node as any).text`/`.name` and `getNodeText(prop, '')` with an empty source,
both of which return nothing for web-tree-sitter nodes, so `.forEach`/`.map`/
`.filter` callbacks were never recognized as implicit loops. It now reads the
property text via `getNodeText(prop, sourceCode)` — the same extraction
`memberPropertyName` uses. This was a dead path that the corpus's `forEach` pin
(`n-plus-one.ts:51`) exposed; the unit test
`spec-17.test.ts` "per-item `.prepare().get()` in a loop fires" and the corpus
now pin both halves.

### Driver-method gap (the report)

The eager set now covers D1's surface plus `.get()`. The eager methods that
better-sqlite3, `node:sqlite`, and `bun:sqlite` expose and D1 does not, and
their coverage status, are:

| driver | eager method | what it does | covered? |
|---|---|---|---|
| better-sqlite3 | `.get()` | single row (or `undefined`) | ✓ Fix 5 |
| better-sqlite3 | `.iterate()` | lazy row iterator | ✗ |
| node:sqlite | `.get()` | single row (or `undefined`) | ✓ Fix 5 |
| node:sqlite | `.iterate()` | lazy row iterator | ✗ |
| bun:sqlite | `.get()` | single row (or `undefined`) | ✓ Fix 5 |
| bun:sqlite | `.values()` | all rows as arrays | ✗ |
| bun:sqlite | `.iterate()` | lazy row iterator | ✗ |

(`.all()` / `.run()` / `.exec()` are already in the set; `.raw()` is both a D1
method and a better-sqlite3 chain modifier, and is covered.)

`.iterate()` (all three) and bun's `.values()` are real eager reads a loop could
abuse, but they are deliberately left out for now: `.iterate()` defers I/O to
the first `.next()`, so a loop that *builds* iterators without consuming them is
not an N+1, and adding it pre-emptively would over-fire until a corpus fixture
proves a false negative. Recorded here as a known gap, not silently dropped.
