## The working list (12 disagreements)

### A. `loop-query` false negatives — `.get()` is not an eager method (2)

| file:line | expected | actual | root cause |
|---|---|---|---|
| `n-plus-one.ts:51` | fire (forEach `.prepare().get()`) | quiet | `EAGER_DB_METHODS = {run, all, first, raw, exec, batch, query}` omits `get`, so `db.prepare(…).get(…)` is misclassified by `isStatementConstructionOnly` as statement-construction-only and skipped |
| `n-plus-one.ts:62` | fire (while `.prepare().get()`) | quiet | same — `.get()` (better-sqlite3) is a real eager read, but the eager set only knows D1's `.all()`/`.first()`/`.run()` |

`for…of` + `.all()` (line 41) and the nested `for` + `.run()` (line 73) fire
correctly — the gap is specifically `.get()`. One fix: add `get` to
`EAGER_DB_METHODS` (and check whether `DB_CALL_METHODS` also needs it).

### B. `missing-org-filter` false positives — unshared predicate vocabulary (4)

The `hasOrganizationFilter` predicate detector runs on the fixed 8-entry
`organizationPatterns` (`organizationId`/`organization_id`/`orgId`/`org_id`/
`tenantId`/`tenant_id`/`companyId`/`company_id`). It is **not** shared with the
tenant-column list. A table whose tenant column is `workspace_id`/`team_id`/
`project_id`/`environment_id` is discovered as tenant by Tier 1, but its scoping
predicate is invisible to the predicate detector → every correctly-scoped query
fires `critical`.

| file:line | expected | actual | root cause |
|---|---|---|---|
| `tenant-scoping.ts:145` | quiet (`workspaceId` scoped) | critical | `workspace_id` not in `organizationPatterns` |
| `tenant-scoping.ts:153` | quiet (`teamId` scoped) | critical | `team_id` not in `organizationPatterns` |
| `tenant-scoping.ts:161` | quiet (`projectId` scoped) | critical | `project_id` not in `organizationPatterns` |
| `tenant-scoping.ts:169` | quiet (`environmentId` scoped) | critical | `environment_id` not in `organizationPatterns` |

  `tenant-scoping.ts:133`) is **correctly quiet** but for an *incidental* reason:
  the tag's template is a direct child of the call (no `arguments` node), so
  `isDynamicStringConstruction` never recurses into it. Correct result, unsteady
  mechanism — a raw interpolation inside a tag would be missed the same way.
  Worth an explicit corpus case in the injection slice if we want to pin it.
